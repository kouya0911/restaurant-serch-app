# デモガイド（行く日登録 → 行ったよ認証 → レビュー → 店長ページ）

所要 約 4 分 20 秒。PC 1 台（店長ページ）＋スマホ 1〜2 台（利用者）。
使う SQL は `docs/sql/005_demo_status.sql`（状況確認）と `docs/sql/005_demo_reset.sql`（リセット）。

## 0. 役割と持ち物

| 役 | 機材 | やること |
|---|---|---|
| 店長役（PC） | PC + 大きな画面/プロジェクター | 店長ページを全画面で映す。認証コードを読み上げる |
| 利用者A（スマホ1） | デモ用アカウントでログイン済み | **開始前に**今日の予定を登録しておく → 本番では時間帯の選び方を見せて「行ったよ」→ レビューまで行う |
| 利用者B（スマホ2・任意） | 別のデモ用アカウント | 本番中にその場で予定登録だけ行う（予定が増える様子と、来店率 50% を見せるため） |

スマホは 1 台でも成立する（その場合は「B の場面」を省く）。人数を 1 人で回す場合は、PC 操作は台本の間だけ触れば済むようにしてある（PC は画面を映しっぱなしにするだけ）。

## 1. 前日までの準備

- [ ] **デプロイ先を決める**。スマホからアクセスできる URL が必要（`localhost` はスマホから開けない）。
  - このブランチ（`feature/visit-plans`）が本番/プレビューにデプロイされているか、Vercel で確認する。
  - Vercel の環境変数（`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `GOOGLE_API_KEY`, `OPENAI_API_KEY` など）が設定済みか。
  - Supabase の Authentication > URL Configuration に、デモで使う URL（プレビューURLは変わる）が Redirect URLs として許可されているか。Google ログインが通らないと何も始まらない。
  - プレビューデプロイで Vercel の「Deployment Protection」が有効だと、ログインしていない端末で店長ページが開けないことがある。
  - ※ これらは私の側では確認できていない。必ず事前に実機で通しリハーサルをして確かめる。
- [ ] **SQL が本番の Supabase に実行済み**か（`001`〜`004`、`006`〜`010`。`002/003/004/006/007/008/009/010` のテストが全部 OK か）。
- [ ] **デモ用アカウントを用意**する。サイドバーに **名前とアイコンが表示される**ため、個人の Google アカウントだと画面共有/録画に写る。デモ専用の Google アカウントを推奨。
- [ ] 各スマホで **デモ用アカウントにログイン**し、**住所を設定**しておく（トップページの「近くのお店」に使われる）。
- [ ] **デモ店をお気に入りに入れておく**（探す手間を省く）。サイドバー > お気に入り > 店名をタップ > 詳細モーダル、の動線で開けるようにする。
- [ ] `stores` にそのデモ店が登録され、認証コードが台本どおり（`1234`）か（`005_demo_status.sql`）。
- [ ] 店長ページの URL を作ってブックマーク: `https://<デモのドメイン>/store/<トークン>`（`005_demo_status.sql` の `store_page_path`）。**URL は他人に見せない**（見られたら `005_demo_reset.sql` のブロック F で作り直せる）。

## 2. 当日の直前チェックリスト（開始 30 分前 → 5 分前）

**ネットワーク**
- [ ] PC・スマホともに安定した回線につながっている（会場 Wi-Fi が不安なら、スマホのテザリング/モバイル回線を予備に）。
- [ ] スマホのブラウザで、デモの URL が開ける。

**ログイン状態**
- [ ] スマホ A・B がログイン済み（サイドバーに名前が出る）。セッション切れがないか、30 分前に一度アプリを開いて確認。
- [ ] PC の店長ページは **ログインなしで開ける**（シークレットウィンドウで確認するのが確実）。

**データ**
- [ ] `005_demo_reset.sql`（ブロック A）で今日の予定を消し、`005_demo_status.sql` で `today_planned = 0 / today_visited = 0 / today_reviews = 0`（今日の予定のレビューも一緒に消える）。
- [ ] **開始 30 分前〜直前**: スマホ A でデモ店に **今日の予定を登録**（時間帯はどれでもよい）→ `005_demo_reset.sql` の **ブロック H だけを選択して Run** → `005_demo_status.sql` で `today_planned = 1`。
  - 「行ったよ」は「時間帯の始まりの 1 時間以上前に宣言」かつ「始まりの 15 分前〜3 時間後」しか通らない。本番中に登録した予定はすぐには認証できないので、A の予定は事前に登録し、ブロック H で「今の時台・2 時間前に宣言」に直しておく。
  - H をかけてから **3 時間以内**に「行ったよ」まで終える。開始が遅れて時台をまたいでも、3 時間以内なら大丈夫。
  - スマホ A のサイドバーで、その予定に **「行ったよ」ボタンが出ている**ことを確認（出ていなければ H をもう一度）。
- [ ] `min_display_count = 1`（デモ用の閾値。3 のままだと 1〜2 人のとき「少数」と伏せられて数字が出ない）。
- [ ] `verify_code = 1234`。
- [ ] スマホ A のサイドバーで「電気代還元ポイント」の今の値を見ておく（台本 2:50 で「10pt 増えた」と見せるため。リセットで今日の予定を消すと、その分のポイントも戻る）。

**画面・端末**
- [ ] **店長ページのタブを最前面にして全画面（F11）**。ブラウザは背面や最小化のタブだと **自動更新が止まる**。別ウィンドウの資料と切り替えるときは、必ず店長ページに戻す。
- [ ] PC の表示倍率を確認（大きな画面なら 100〜125%）。店長ページは **スクロールなしの 1 画面**で、左列（今日の予定・来店・来店率、認証コード、今後 7 日の予定、お客様の声）と右列（電力データ × 来店予測の構想イメージ）が同時に見えること。スクロールが出るなら倍率を下げる。
- [ ] 数字が変わったときの目印は、数字の横に **小さく「更新」** と約 5 秒出るだけ（光ったり大きくなったりはしない）。会場の画面では気づきにくいので、変わった数字は指し示しながら話す。
- [ ] スマホ: **自動ロックを長めに**、**おやすみモード/通知オフ**、画面の明るさを上げる。
- [ ] 通知（メール・チャット）が PC 画面に出ないようにする。
- [ ] 台本のセリフと順番を頭に入れる。1 回は通しで練習する（下の「リハーサル」）。

## 3. デモ台本（約 4 分 20 秒）

数字の反映は **最大 5 秒**かかる。反映を待つ間は、次の「セリフ」を話してつなぐ。

| 時間 | 誰が | 操作 | セリフ（例） |
|---|---|---|---|
| 0:00–0:25 | 店長役（PC） | 店長ページを映す（スクロールなしの 1 画面）。左上の「今日」が 予定 1人 / 来店 0人（A が開始前に登録した分）、その右に認証コード `1234` | 「お店の方は、今日何人来てくれるのか、予約した人が本当に来たのか、なかなか見えません。これは、お店専用の画面です。ログインは要らず、お店だけが知る URL で開きます。今日はすでに 1 人が『行く』と宣言しています。」 |
| 0:25–0:55 | 利用者A（スマホ1） | サイドバー > お気に入りのデモ店 > 詳細モーダル。**「今日の行く予定」の棒**（今の時台に 1）を見せる → **「行く日をカレンダーに追加」** を開いて **時間帯のボタン**を見せ、**キャンセル**（登録はしない） | 「お客さんは、行く日と時間帯を宣言します。来店の証明に使えるのは、時間帯の 1 時間前までに宣言した予定だけです。私は先ほど宣言しておきました。お店ごとに、何時台に何人行く予定かも見えます。誰が行くかは出ません。」 |
| 0:55–1:25 | 利用者B（スマホ2・任意） | 同じお店の予定を **今日**で登録。時間帯は **2 時間以上先**を選ぶ（近い時間帯だと「この時間だと来店認証ができません」の注意が出る）→ PC の「今日」の **予定** が **2** になり、横に小さく「更新」。左下の「今後 7 日の予定」の今日の棒も伸びる | 「もう 1 人、宣言します。登録すると、お店側の画面に数秒で反映されます。」 |
| 1:25–2:05 | 利用者A（スマホ1） | サイドバー > 「これから行く」> 今日の予定の **「行ったよ」** > コード入力（PC に映っている `1234`）> **「認証する」**。「来店を記録しました」の横に小さく **「+5pt」** が出るのを確認（ダイアログは閉じずにレビューへ進む） | 「お店に着いたら『行ったよ』を押して、お店に掲示されているコードを入れます。お店にいないと分からない番号なので、来たことの証明になります。来店すると 5 ポイントもらえます。」 |
| 2:05–2:25 | 店長役（PC） | 「今日」の **来店** が **1** になり「更新」が出る。来店率が **50%**（B が登録した場合。B がいなければ 100%） | 「お店の画面では、予定 2 人のうち 1 人が実際に来店した、と分かります。『行くと言って来なかった人』も見えるので、仕込みの目安になります。」 |
| 2:25–2:50 | 利用者A（スマホ1） | 「来店を記録しました」の下のレビュー欄で **星 5** をタップ、ひとこと「おいしかった！」> **「送る」**。「レビューを送りました」の横に **「+5pt」** が出るのを確認して閉じる | 「来店を認証した人だけが、そのままレビューを書けます。行っていない人の口コミは入りません。レビューを書くと、さらに 5 ポイントです。」 |
| 2:50–3:10 | 利用者A（スマホ1） | サイドバー（≡）を開き、ユーザー名の下の **「電気代還元ポイント」** が来店前より **10pt** 増えているのを見せる。その下の小さな「※ 電気代への還元はイメージです」も指す | 「来店とレビューで、ポイントが 10 ポイント増えました。**このポイントを電気代に還元する仕組みは、まだイメージの段階です。** お店に行くほど家の電気代がお得になる、という形を目指しています。」 |
| 3:10–3:30 | 店長役（PC） | 左下の「お客様の声」を指す。最近のレビューの先頭に ★5「おいしかった！」が出て、件数の横に「更新」。平均と件数も変わる | 「お店には、星とひとことが数秒で届きます。書いた人の名前は出ません。」 |
| 3:30–3:45 | 店長役（PC） | 左列の一番下の注記を指す | 「個人の名前は見えません。人数だけです。少人数の日は個人が特定されないように『少数』と表示します。今日は説明のため、少人数でも数字が出る設定にしています。」 |
| 3:45–4:20 | 店長役（PC） | 右列「電力データ × 来店予測」を指す。見出し横の **「構想イメージ（サンプルデータ）」** のラベルを最初に指してから、電力の折れ線 → 明日の予測来店数 → おすすめ、の順に | 「**ここから右側は、まだ実際のデータではなく、構想のイメージです。数字はすべて説明用のサンプルです。** 今後、お店の電力の使い方と、この来店の記録を組み合わせて、明日何人来そうか、仕込みをどれくらいにするか、空調のピークをどうずらすか、まで提案できるようにしたいと考えています。」 |

**スマホ 1 台のとき**: 0:55–1:25 の B の場面を省く（予定は 1 人のまま、来店率は 100%）。
**注意して言う 1 文（推奨）**: 閾値を下げてデモしていることは正直に伝える。3:30 のセリフの最後の一文がそれ。
**ポイントの還元は必ず「イメージ」と言う（必須）**: ポイントは来店・レビューの記録から計算して表示しているだけで、電気代への還元の仕組みはまだ無い。2:50 のセリフの太字部分は省略しない。
**右列は必ず「サンプル」と言う（必須）**: 左列は本物のデータ、右列は固定のサンプルデータで、実際の電力データとはつながっていない。3:45 のセリフの太字部分は省略しない。時間が押した場合は右列の説明を短くしてよいが、「構想イメージで、数字はサンプル」の一文だけは必ず言う。質問で右列の数字の根拠を聞かれたら「説明用の架空の数値です」と答える。
**レビューを「あとで」にした場合**: サイドバー（≡）>「レビューを書く」から同じ入力欄を開ける。台本どおりにその場で書くのが基本。
**「お客様の声」の過去のレビュー**: 友達に使ってもらった期間のレビューも、平均と件数に入り、最近の 3 件が並ぶ。書かれた内容は事前に `005_demo_status.sql` の件数と、店長ページで目視しておく（本番で想定外の文が映らないように）。
**友達の実データ**: ピッチまでの数日間に友達に実際に使ってもらったデータ（`docs/demo/friend-guide.md`）は、「お客様の声」の平均・件数・最近のレビューと、「今後 7 日の予定」（友達が先の日付で登録した分）に出る。左列はサンプルではなく実データなので、「この数日間、友達に使ってもらった実際の記録です」と一言添える（右列のサンプルと混同させない）。

## 4. リハーサル手順（本番前に何度でも）

1. `005_demo_reset.sql` を **そのまま全文 Run**（ブロック A = デモ店の今日の予定を全部消す）。
2. `005_demo_status.sql` を Run し、`today_planned = 0`、`today_visited = 0` を確認。
3. スマホ A で今日の予定を登録 → ブロック H だけを選択して Run → `today_planned = 1` と、サイドバーに「行ったよ」が出ていることを確認。
4. 台本どおりに通しで操作する（スマホ 1〜2 台 + PC）。
5. 終わったらもう一度 1 → 3。
- 「行ったよ」からやり直したいだけなら、ブロック B（来店の記録とその予定のレビューを戻す）を、そのブロックだけ選択して Run。
- レビューの送信だけやり直したいなら、ブロック G（今日の予定のレビューだけ消す）。来店済みのまま、サイドバーの「レビューを書く」から送り直せる。
- 片方のスマホのアカウントだけリセットしたいなら、ブロック C（メールアドレス指定）。
- リセットが触るのは **stores に登録されたデモ店の visit_plans と、そのレビューだけ**。他の店・お気に入り・住所・stores 自体は変わらない。
- **友達の実データを貯めている期間は、ブロック D（全期間削除）を使わない。** ブロック A・B・C は「今日」の分だけを対象にするので、過去の実データは残る（ただし今日の分は消える）。
  デモ当日の朝にブロック A を流すと、当日分だけがリセットされ、過去の実データ（過去の日のレビューなど）はそのまま残る。

## 5. 万一のとき

| 症状 | 対応 |
|---|---|
| 店長ページの数字が増えない | 5 秒待つ → まだなら F5 で再読み込み。タブが背面でないか確認。それでも駄目なら「ネットワーク」を疑い、テザリングに切替 |
| 画面に「通信できませんでした」の細い帯 | 一時的な通信切れ。自動で再試行する。続くなら F5 |
| 店長ページが 1 画面に収まらずスクロールが出る | ブラウザの表示倍率を下げる（Ctrl + −）か F11 で全画面にする |
| 「このページは無効になりました」 | URL のトークンが変わった（ブロック F を実行した等）。`005_demo_status.sql` で新しい URL を取り直す |
| スマホで「この店はその日にすでに登録されています」 | 前回のリハーサルの残り。ブロック A でリセット |
| 「認証コードが違います」 | PC の店長ページに映っているコードを確認して入れ直す（全角でも通る） |
| 「この店はまだ来店認証に対応していません」 | その店が `stores` に無い。`005_demo_status.sql` で確認 |
| 「来店の認証ができるのは、予定の日当日だけです」 | 時間未定の古い予定で、日付が今日でない。ブロック A でリセットして登録し直す |
| 「来店の認証は、予定の時間帯が始まる15分前からできます」/「…1時間前までに宣言した予定だけ…」/「…3時間後までです」 | ブロック H をかけ忘れた、またはかけてから 3 時間以上たった。ブロック H だけを選択して Run し、もう一度「行ったよ」 |
| サイドバーに「行ったよ」ボタンが出ない（「この時間だと来店認証ができません」と出る） | 同上。ブロック H を Run すると、1 分以内にボタンが出る（サイドバーを開き直すとすぐ出る） |
| 「お客様の声」に新しいレビューが出ない | 5 秒待つ → まだなら F5。`005_demo_status.sql` の `today_reviews` が増えていれば DB には届いている |
| 「この予定にはすでにレビューを書いています」 | 前回のリハーサルの残り。ブロック G（レビューだけ消す）か A（予定ごと消す） |
| レビュー欄を「あとで」で閉じてしまった | サイドバー（≡）>「レビューを書く」から書ける |
| スマホでログインできない | 予備のアカウント/端末に切り替え。事前に Redirect URL の許可を確認しておく |
| 会場の回線が完全に駄目 | 下の「予備の映像」に切り替える |

## 6. 予備の映像（録画・スクリーンショット）の撮り方

**先にやること**: リハーサル手順の 1〜2 でリセットし、通知を切り、デモ用アカウントであることを確認する（サイドバーの名前/アイコンが写る）。**撮影後、店長ページの URL が映った場合は `005_demo_reset.sql` のブロック F で URL を作り直す。**

**最小構成の予備（これだけは必ず撮る）**
1. **PC 画面の録画（60 秒程度）**: 店長ページが 0/0 → 予定 +1 → 来店 +1 になる様子。
   - Windows: `Win + Alt + R`（Xbox Game Bar。事前に `Win + G` で有効化しておく）で開始/停止。動画は「ビデオ > キャプチャ」に保存される。
   - 別案: OBS Studio（無料）で画面キャプチャ。
2. **スクリーンショット 3 枚**（`Win + Shift + S`）:
   ① 0人/0人の状態 ② 予定が増えた状態 ③ 来店が増えた状態（来店率つき） ④ 「お客様の声」に新しいレビューが出た状態（右列の構想イメージも同じ画面に写る）。
3. **スマホ操作のスクリーンショット/画面録画**:
   - iPhone: 設定 > コントロールセンター で「画面収録」を追加 → コントロールセンターから録画開始/停止。
   - Android: クイック設定の「スクリーンレコード」。
   - 撮るのは「行く日をカレンダーに追加 → 登録しました」「行ったよ → コード入力 → 来店を記録しました」「星とひとこと → レビューを送りました」の 3 場面。

**もっとよく撮る（余裕があれば）**
- スマホと PC を 1 つのカメラで一緒に撮る（別のスマホで撮影）。どの操作でどの数字が変わったかが 1 本で伝わる。
- 録画はデモの通りの順で。撮ったあと、無音でも意味が通じるようにスライドの上で字幕を入れるか、当日は声で説明する。

**予備の使い方**: 回線障害のときは「実際のお店の画面をお見せしたかったのですが、録画で説明します」と伝えて動画を再生し、台本のセリフをそのまま当てる。

## 7. 質問への備え（短く）

- **個人情報は？** 店には人数しか渡さない。氏名・ID・時刻は返さない。少人数の日は「少数」と伏せる（DB 側で処理）。
- **コードを共有されたら？** 今回はコードは店ごとの固定値。日替わりコード・位置情報の併用は今後の課題。
- **URL が漏れたら？** URL を作り直せば古い URL は即座に無効になる。
- **来店率の「予定」はどう数える？** 「行く日と時間帯」を宣言した人。来店の認証は、時間帯の 1 時間前までに宣言した予定で、時間帯の始まりの 15 分前〜3 時間後だけできる（その場で宣言してすぐ認証、はできない）。デモでは、事前に宣言した予定の時刻を SQL で今の時台に合わせている。
- **一覧や詳細の「〇時台 〇人予定」は？** アプリで宣言した人数だけ（誰が宣言したかは返さない）。実際の混雑とは異なる場合がある。今はログインした人だけが見られる。
- **電気代還元ポイントは本当に還元されるの？** まだされない。今は来店認証 1 件 5pt、レビュー 1 件 5pt を、利用者の来店記録から計算して表示しているだけ（ポイント用のデータは保存していない）。電気代への還元は、電力会社との連携を含めた今後の構想。
- **右側の電力データや予測は動いているの？** まだ動いていない。右列は構想のイメージで、数字はすべて説明用のサンプル（コードに固定で書いた架空の値）。今後、お店の電力データ（スマートメーター等）と来店の記録を組み合わせて予測する構想。
- **やらせレビューは？** レビューを書けるのは、来店認証した自分の予定だけ、予定 1 件につき 1 件（DB 側で強制）。行っていない人は書けない。
- **レビューから個人が分かる？** 店には星とひとことだけを渡し、名前・ID・日時は返さない。ただし今回はデモのため、少人数の店で「今来た人が書いた」と推測されにくくする工夫（一定件数が貯まるまで伏せる・表示を遅らせる等）は入れていない。本番では入れる予定。
